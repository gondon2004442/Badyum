# Badyum

Голосовые каналы вне зависимости от геолокации. Канал живёт всегда: зашёл —
уже говоришь, без дозвона и без «принять/отклонить». Работает с ПК во время
игры и с телефона в браузере.

## Что уже есть

- Голосовой канал на WebRTC P2P mesh, до 8 человек (настраивается).
- Вход по инвайт-ссылке `/j/<код>` и по кодовому слову `/r/<слово>`, плюс QR
  прямо на экране канала.
- Гостевой вход: чтобы попасть в звонок, нужно только имя.
- Экран канала: плитки участников, кольцо говорящего, мьют, «оглохнуть»,
  громкость на каждого участника, push-to-talk, индикатор качества связи.
- Текстовый чат канала рядом с голосом.
- Сайдбар с каналами, куда ты заходил, и панель людей.
- Мобильная раскладка с учётом safe-area и крупными зонами нажатия.

## Быстрый старт

```bash
pnpm install
pnpm dev
```

Поднимутся сервер (`:8787`) и клиент (`:5173`). В логе сервера будет ссылка на
тестовый канал вида `http://localhost:5173/j/zzw2na` — открой её в двух окнах
браузера (второе лучше в режиме инкогнито: имя запоминается в localStorage).

### Как проверить с телефона или с другом

**Локальный IP не подойдёт.** Браузер отдаёт микрофон только в защищённом
контексте — https или localhost. По `http://192.168.x.x:5173` объект
`navigator.mediaDevices` просто не существует, и разрешать тут нечего.

Самый короткий путь — https-туннель до дев-сервера:

```bash
cloudflared tunnel --url http://localhost:5173
```

Туннель отдаст адрес вида `https://что-то.trycloudflare.com` — по нему
работают и страница, и API, и WebSocket (Vite проксирует их сам, так что
настраивать ничего не нужно). Этот адрес можно открыть на телефоне и отправить
другу.

`.trycloudflare.com` и оба наших домена перечислены в `server.allowedHosts`
(`packages/client/vite.config.ts`). Без этого Vite отвечает «Blocked request»
вместо приложения: он защищается от DNS rebinding и по умолчанию пускает только
localhost, а через туннель Host приходит чужой.

Relay при этом нужен настоящий — задай ключи Cloudflare, иначе друг из мобильной
сети не подключится:

```bash
BADYUM_CF_TURN_KEY_ID=<id> BADYUM_CF_TURN_API_TOKEN=<токен> pnpm dev
```

Этого достаточно, чтобы позвать нескольких живых людей: своя машина вместо
сервера, ноль затрат. Ограничения ровно два и оба очевидные — компьютер должен
быть включён, а адрес туннеля меняется при перезапуске, и вместе с ним умирают
розданные ссылки (каналы пока живут в памяти процесса).

## Релиз

Чтобы приложение работало не только на твоём компьютере, нужен постоянный адрес
в интернете. Путей два: Cloudflare Workers (бесплатно, без сервера) или своя
VPS с Docker.

### Cloudflare Workers — путь по умолчанию

Ни сервера, ни туннеля: страница, API и сигналинг живут в одном Worker,
комнаты — в Durable Objects, каналы переживают перезапуск.

```bash
cd packages/worker
npx wrangler login

# Секреты: в репозиторий они не попадают.
npx wrangler secret put BADYUM_TOKEN_SECRET      # openssl rand -hex 32
npx wrangler secret put BADYUM_CF_TURN_KEY_ID
npx wrangler secret put BADYUM_CF_TURN_API_TOKEN

pnpm release
```

Обновить уже выложенный сервис — одна команда, и её же можно звать из корня
репозитория:

```bash
git pull origin main && pnpm install && pnpm release
```

Адрес будет вида `https://badyum.<твой>.workers.dev` и работает сразу. Свой
домен подключается отдельно: домен должен быть в Cloudflare (перевод
NS-записей), после чего в панели Workers добавляется Custom Domain.

Локально то же самое поднимается на настоящем workerd:

```bash
cp packages/worker/.dev.vars.example packages/worker/.dev.vars   # заполнить
pnpm --filter @badyum/worker dev:worker
```

Секреты wrangler читает именно из `.dev.vars` — переменные окружения оболочки
до Worker'а не доезжают.

### Аккаунты (необязательно)

Гостевой вход работает без всего этого и работать не перестанет: аккаунт даёт
постоянный юз `@dumax`, по которому человека находят и добавляют в контакты, а
не право говорить.

Юз человек выбирает сам при первом входе и он уникален на весь сервис. Только
латиница, цифры, точка и подчёркивание — причины две. Первая: продиктовать юз
должен мочь и собеседник с другой раскладкой. Вторая важнее: кириллические «а»,
«е», «о», «р», «с» неотличимы на вид от латинских, и `дumax` рядом с `dumax` —
это не опечатка, а способ выдать себя за другого.

```bash
cd packages/worker
# База уже создана, database_id прописан в wrangler.jsonc. Для новой:
#   npx wrangler d1 create <имя>  — или в панели: Storage & Databases → D1
npx wrangler d1 migrations apply badyuma

# Google Cloud Console → APIs & Services → Credentials → OAuth client ID
# (тип «Web application»). В Authorized redirect URIs перечислить каждый адрес,
# с которого сервис отвечает:
#   https://badyum.<аккаунт>.workers.dev/api/auth/google/callback
#   https://badyum.ru/api/auth/google/callback
npx wrangler secret put BADYUM_GOOGLE_CLIENT_ID
npx wrangler secret put BADYUM_GOOGLE_CLIENT_SECRET
```

Пока секреты не заданы, `/api/me` отвечает `googleEnabled: false`, и клиент не
показывает кнопку входа — предлагать то, что не настроено, хуже, чем не
предлагать вовсе.

**Заводить каналы могут только вошедшие.** Канал в каталоге стоит одного
запроса и остаётся там навсегда, а адресов у того, кто это делает нарочно,
сколько угодно. Правило одно на оба пути создания — кнопку «Новый канал» и
свободное кодовое слово: закрыть один и оставить второй значит не закрыть
ничего. Сверх того — двадцать каналов в час на аккаунт.

Входа это не касается вовсе: по ссылке-приглашению, по занятому кодовому слову
и по id канала пускают кого угодно, без регистрации, по одному имени. На этом
держится весь продукт, и трогать это нельзя.

Там, где вход не настроен (локальная разработка, чужая копия), требовать его
нечестно — иначе завести канал было бы нечем. Тогда, как раньше, ограничение
считается по адресу.

**Ограничение бесплатного плана:** 100 000 запросов в сутки, и каждое сообщение
WebSocket считается запросом. Ping и pong обслуживает сама платформа
(`setWebSocketAutoResponse`) и объект при этом не будит, но индикатор речи шлёт
`state` при каждом изменении — вчетвером это тысячи сообщений в час. Для
небольшой компании запас есть; платный план стоит $5 и поднимает лимит на два
порядка.

### Из России сайт не открывается без VPN

Известное ограничение, и оно не в коде. Из российских сетей ответ от Cloudflare
обрывается примерно на 24 килобайтах — соединение остаётся живым, но данные
перестают идти. Мелкие ответы проскакивают, страница целиком — нет.

Четыре измерения одного и того же файла, `curl` с домашней сети:

| откуда | скачано из 341 730 |
|---|---|
| `badyum.ru`, с VPN | 25 358 → стоп |
| `badyum.ru`, без VPN | 25 366 → стоп |
| `badyum.<аккаунт>.workers.dev` | 23 961 → стоп |
| `badyum.ru` после выключения ECH | 24 326 → стоп |

Что проверено и **не** помогло: свой домен вместо `workers.dev`, выключение
Encrypted ClientHello (`PATCH /zones/{id}/settings/ech` со значением `off` —
переключателя в панели нет), понижение минимальной версии TLS. Дробить сборку
тоже бесполезно: под потолок не проходит даже CSS.

Симптом в браузере — `ERR_CONNECTION_RESET` или бесконечная загрузка при том,
что `curl` к `/api/health` отвечает мгновенно. Не ищите ошибку в коде: разница
между ними в размере ответа, а не в маршруте.

Сознательное решение — жить с этим: заграничные собеседники заходят напрямую,
российские через VPN. Цена решения: позвать человека в России «просто по
ссылке» не получится.

Если это станет мешать, выход — перенести сервис на машину, доступную из
России. Он по силам: `packages/core` намеренно написано без привязки к
рантайму (Web Crypto вместо `node:*`), и заявки в друзья, лимиты, токены и
каналы переносятся как есть. Переложить придётся хранилище (D1 → SQLite) и
Durable Objects (комнаты и присутствие → обычные объекты в процессе).

### Своя VPS с Docker

Вариант, если Cloudflare не подходит.

#### 1. Сервер

Понадобится VPS и домен, направленный на него A-записью. Проект рассчитан на
два: **badyum.ru** и **badyum.online** — Caddy получит сертификат на оба, и
второй остаётся запасным входом, если первый окажется недоступен.

Дальше:

```bash
git clone https://github.com/gondon2004442/Badyum.git
cd Badyum
cp infra/.env.example infra/.env
# домены уже проставлены; заполни секреты (openssl rand -hex 32) и ключи relay
docker compose -f infra/docker-compose.prod.yml --env-file infra/.env up -d --build
```

Поднимутся два контейнера: статика клиента за Caddy и сигналинг. HTTPS Caddy
получит сам — отдельно ничего настраивать не нужно, а он здесь обязателен: без
защищённого соединения браузер не отдаёт микрофон.

В файрволе VPS достаточно открыть `80` и `443`. Relay по умолчанию managed
(Cloudflare), поэтому UDP-портов и белого IPv4 не требуется — они нужны только
своему coturn, см. ниже.

Проверка: `curl https://badyum.ru/api/health` должен вернуть
`"turnConfigured": true`. Если там `false` — relay не настроен, и звонки между
разными сетями будут молча не соединяться, хотя локально всё выглядит рабочим.
Поле `turn` в том же ответе показывает, какой именно путь живой.

#### 2. Телефон

Отдельного приложения не нужно: открой сайт в браузере телефона и добавь на
домашний экран — «Установить приложение» в Chrome, «На экран Домой» в Safari.
Откроется без адресной строки и вкладок, с иконкой, как обычное приложение.

Звонок при этом живёт, пока приложение открыто; работа при заблокированном
экране — это уже нативная обёртка, её пока нет.

### 3. Установщики для компьютера

Собираются автоматически по тегу. Один раз задай адрес сервера: **Settings →
Secrets and variables → Actions → Variables**, переменная `BADYUM_SERVER_URL`
со значением `https://badyum.ru`. Без неё сборка намеренно падает — иначе
получился бы установщик, который никуда не подключается.

```bash
git tag v0.1.0
git push origin v0.1.0
```

GitHub соберёт `.msi` для Windows, `.dmg` для macOS и `.AppImage`/`.deb` для
Linux и положит их в черновик релиза — останется нажать «Publish».

Установщики не подписаны, поэтому при первом запуске Windows покажет
«SmartScreen», а macOS — «неизвестный разработчик». Это лечится только платными
сертификатами разработчика.

## Десктопное приложение

```bash
pnpm --filter @badyum/desktop dev     # окно приложения + сервер + клиент
pnpm --filter @badyum/desktop build   # собрать бинарник и пакеты
```

Приложение — это тот же клиент в нативном окне, но с одной вещью, которой в
браузере быть не может: **рация работает поверх игры**. Системный хоткей `F8`
перехватывается на уровне ОС, поэтому свернув окно в игру, ты не теряешь
возможность говорить. В браузере клавиша живёт только пока вкладка в фокусе — и
это единственная причина, по которой обёртка вообще существует.

Адрес сервера зашивается в сборку из
[`packages/client/.env.desktop`](packages/client/.env.desktop): страница
загружается из локальных файлов, относительный путь оттуда никуда не ведёт. Для
релиза поменяй значение на адрес своего сервера.

Сервер должен разрешать источник приложения — добавь его в `BADYUM_ORIGINS`:

```bash
export BADYUM_ORIGINS="https://badyum.ru,https://badyum.online,tauri://localhost,http://tauri.localhost"
```

Для сборки на Linux нужны системные библиотеки:

```bash
sudo apt install libwebkit2gtk-4.1-dev build-essential libxdo-dev \
  libssl-dev libayatana-appindicator3-dev librsvg2-dev
```

## Архитектура

```
packages/
  shared/   протокол сигналинга (zod-схемы, общие типы клиента и сервера)
  server/   Fastify + WebSocket-хаб: комнаты, инвайты, релей SDP/ICE
  client/   React + Vite: движок звука и экраны
apps/
  desktop/  Tauri-обёртка: окно, глобальная рация, доступ к микрофону
infra/      Docker-образы, Caddy и coturn
```

### Ключевое решение: `VoiceEngine`

Mesh и SFU отличаются ровно одним — откуда берутся медиапотоки. Всё остальное
(состав комнаты, индикация речи, мьюты, громкости) одинаково. Поэтому UI
разговаривает только с интерфейсом
[`VoiceEngine`](packages/client/src/voice/VoiceEngine.ts), а под ним лежит
[`MeshEngine`](packages/client/src/voice/MeshEngine.ts). Переезд на SFU —
вторая реализация того же интерфейса; экраны не меняются.

**Правило:** ни один React-компонент не импортирует `RTCPeerConnection`,
`MediaStream` или SDK SFU напрямую — только `useVoice()`.

### Сервер не видит медиа

Сигналинг знает лишь «кто в какой комнате» и пересылает конверты `signal`
адресату. SDP он не разбирает. Это весь бэкенд звонка.

### Все способы входа сходятся в одну точку

Ссылка, QR (это та же ссылка), кодовое слово и id канала резолвятся в
`channelId` в [`ChannelStore.resolve`](packages/server/src/channels.ts), и
дальше идут общим путём. Новый способ связи добавляется там и больше нигде.

## TURN — обязателен, а не опция

Соединению мешает не расстояние, а NAT. Мобильные операторы и корпоративные
сети сидят за symmetric NAT / CGNAT, где прямое P2P не устанавливается никогда.
Без TURN звонки с телефона работают «через раз» и выглядят как плавающий баг.

Аудио через relay — около 40 кбит/с на поток. Даже вчетвером и полностью через
relay это ~540 МБ за час разговора, то есть трафик здесь никогда не будет
узким местом. Узкое место — доступность самого relay.

Поддерживаются два пути, и можно включить оба сразу: тогда WebRTC переберёт
кандидатов сам, и авария у одного из relay останется незаметной.

### Managed relay Cloudflare (по умолчанию)

Бесплатно до 1000 ГБ в месяц, не нужны ни белый IPv4, ни открытый UDP. Плюс
anycast — relay берётся из ближайшей к человеку точки, а не из одного ДЦ, что
для «вне зависимости от геолокации» объективно лучше своего одиночного coturn.

Панель Cloudflare → Realtime → TURN → создать ключ, дальше в `infra/.env`:

```bash
BADYUM_CF_TURN_KEY_ID=<id ключа>
BADYUM_CF_TURN_API_TOKEN=<токен>
```

Креды сервер берёт сам и держит в кэше один набор на всех: у Cloudflare они не
привязаны к пользователю, так что персональные ничего бы не защитили, зато
стоили бы обращения к чужому API на каждый вход в канал. Срок жизни намеренно с
запасом — `RTCPeerConnection` запоминает `iceServers` при создании и держит их
до закрытия, включая ICE restart, поэтому истечение кред посреди разговора
ломало бы relay молча.

### Свой coturn

Нужен, только если managed-вариант не подходит. Требует выделенного белого IPv4
и открытых `3478/udp` + `49160-49200/udp`.

```bash
# в infra/.env
BADYUM_TURN_SECRET=$(openssl rand -hex 32)
BADYUM_TURN_EXTERNAL_IP=<белый IP машины>
BADYUM_TURN_REALM=badyum.ru
BADYUM_TURN_HOSTS=turn:badyum.ru:3478?transport=udp
```

```bash
docker compose -f infra/docker-compose.prod.yml \
               -f infra/docker-compose.coturn.yml --env-file infra/.env up -d
```

Креды выдаются короткоживущие по HMAC-схеме coturn: конфиг клиента виден в
DevTools, и статический пароль превратил бы relay в чужой прокси.

`GET /api/health` показывает `turnConfigured` и разбивку по путям в поле `turn`.

## Проверка

```bash
pnpm test        # юнит-тесты резолвера инвайтов и состояния комнаты
pnpm typecheck
pnpm build
```

Живые сценарии, которые стоит прогонять руками:

1. Два браузера на разных машинах открывают `/j/<код>` — слышат друг друга.
2. **Телефон по мобильному интернету, не по домашнему Wi-Fi.** Только это и
   проверяет «вне геолокации»: на домашнем Wi-Fi TURN не задействуется.
3. TURN-путь принудительно: временно `iceTransportPolicy: "relay"` в
   [`peer.ts`](packages/client/src/voice/peer.ts) — звонок обязан работать.
   Если нет, coturn настроен неверно, и это вскроется только на пользователях.
4. Throttling (Slow 3G, потери): голос деградирует, но соединение не рвётся, а
   индикатор показывает «плохо», а не врёт зелёным.
5. Выдернуть Wi-Fi на 10 секунд — возврат в канал без ручного перезахода.
6. Четверо жмут «войти» одновременно — никто не завис на «Подключаюсь».

Сам WebRTC тестируется в браузере: мокать его дороже и бесполезнее, чем открыть
две вкладки.

## Известные ограничения

- **Глобальный push-to-talk браузер не даёт** — в вебе рация работает, только
  пока вкладка в фокусе. Поверх игры она работает в десктопном приложении.
- **iOS усыпляет звонок при свёрнутом браузере.** PWA закрывает сценарий «сижу
  в канале с телефоном в руках»; «канал в кармане при заблокированном экране» —
  это Capacitor + CallKit, осознанно отложено.
- Mesh честно держит примерно до 6 человек: исходящий трафик растёт линейно с
  числом участников. Дальше нужен SFU.
- Каналы и инвайты живут в памяти процесса — перезапуск сервера их теряет.
